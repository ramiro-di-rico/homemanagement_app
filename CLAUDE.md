## Architecture

This is a **Flutter personal finance app** supporting mobile (Android/iOS), desktop (Linux), and web. It manages accounts, transactions, budgets, recurring payments, and shared household access via invitations.

### Dependency Injection

The app uses **GetIt** as a service locator (no BLoC/Provider/Riverpod). All services and repositories are registered by hand in `lib/main.dart` inside `registerServices()`/`registerSingletons()`, called from `registerDependencies()`. `injectable` is a listed dependency but is **not actually wired up** — there's no `@injectable`/`@Injectable()` codegen in this repo; don't add those annotations expecting them to be picked up. Widgets retrieve dependencies via `GetIt.instance<T>()`.

### Data Flow

```
HTTP Service  →  Repository  →  View (via GetIt)
```

- **`lib/data/services/`** — Raw HTTP calls to the backend API, one class per resource (e.g., `TransactionService`, `AccountService`), plus infra services like `Caching`, `AuthenticationService`, `CryptographyService`, and platform detection (`lib/data/services/platform/`).
- **`lib/data/repositories/`** — Business logic layer that wraps services, handles errors, and aggregates data. Views should call repositories, not services, directly.
- **`lib/data/models/`** — API/deserialization models. **`lib/domain/models/`** — a smaller set of clean domain models (currently just `metrics/`); most features don't have a separate domain layer yet.
- **`lib/ui/features/<feature>/views/`** — Stateful/Stateless widgets that call repositories directly. State is held via `setState` in most features; only `authentication` currently has a `view_models/` folder using `ChangeNotifier` — that MVVM split is the exception, not yet the norm.
- File naming inside `views/` is inconsistent across features (`account.list.dart`, `account-list-desktop.dart`, `main_account.list.dart` all coexist) — match the convention already used in the folder you're editing rather than picking a new one.

### Navigation

GoRouter is configured in `lib/routing.dart`. An authentication guard redirects unauthenticated users to `/login`. Routes under `/home` require authentication. The app supports deep links (handled by `DeepLinkingService`) including QR-scanned invite links.

Key route hierarchy:
- `/login`, `/registration` — auth flow (mobile and desktop variants)
- `/home` — authenticated shell with sub-routes: `/accounts/:id`, `/settings`, `/statistics`, `/budget`, `/transactions/search`, `/bulk-transactions`, `/invites`

### Platform Awareness

`PlatformContext` (in `lib/data/services/platform/`) detects mobile vs. desktop/web at runtime. Many views have separate mobile and desktop implementations (e.g., `LoginView` vs. `DesktopLoginView`). The routing layer (`lib/routing.dart`) picks the variant per-route with a `!isDesktop ? Mobile() : Desktop()` ternary — full-screen variants are separate widget trees, not one responsive widget with breakpoints.

### Authentication & Security

`AuthenticationService` manages JWT tokens, biometric auth (via `local_auth` on mobile), and secure storage. `CryptographyService` provides AES encryption for sensitive local data.

### Key Infrastructure

- **`lib/data/services/caching.dart`** — In-memory cache for API responses
- **`lib/data/services/logger_wrapper.dart`** / **`file_logger_output.dart`** — App-wide logging
- **`lib/data/services/platform/platform_context.dart`** — Platform detection
- **`lib/data/models/`** — Deserialization wrappers for API responses
- **`lib/ui/features/*/view_models/`** — UI-specific data shapes (only present in the `authentication` feature today)

### Localization

Locales are defined via `.arb` files in `lib/l10n/` (`en`, `es`, `es_ar`, `it`, `pt`), configured by `l10n.yaml`. The `app_localizations*.dart` files are generated by `flutter gen-l10n` — never hand-edit them. See the `flutter-add-locale-string` skill for the full workflow.

### Testing

Test coverage is currently minimal (`test/widget_test.dart` smoke test, one model test). No mocking library (`mockito`/`mocktail`) is set up yet — check `pubspec.yaml` before assuming one is available. See the `flutter-write-widget-test` skill for patterns to follow.
